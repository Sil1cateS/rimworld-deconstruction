# 写作规范 v3：演进叙事体

本文件定义 `docs/mechanisms-v3/` 下所有卷的写法。目标读者是**人**：想知道某个子系统到底怎么跑、为什么这么跑、哪一步错了会出什么事的读者。

v1 卷（`docs/mechanisms/`）是**证据优先**：六节骨架 + 断言清单，适合查证，不适合通读。
v3 卷是**理解优先**：一条演进主线 + 阶段下潜 + 分支与契约；断言退到 `## Evidence` 附录做支撑，不再占据正文。

两套并存，v1 冻结不改；v3 从样张卷开始铺开。

---

## 1. 一篇 v3 卷必须做到的事

读者读完应当能自己回答这五个问题（答案必须在正文里，不能靠翻代码）：

| # | 问题 | 落在哪节 |
|---|---|---|
| 1 | 这个子系统解决什么现象？没有它会怎样？ | `## Where it sits` |
| 2 | 状态经过哪几个阶段？每个阶段的触发条件是什么？ | `## Evolution` |
| 3 | 每个阶段由谁推进、以什么额度（每 tick / 250 tick / 每帧 / 事件）推进？ | `## Stage detail` |
| 4 | 底层改了哪些字段或容器？顺序能不能换？换了会怎样？ | `## Stage detail` |
| 5 | 分支在哪，接哪个子系统的口？ | `## Branches` + `## Contracts` |

**读者测试**：随机挑两节，交给没读过该卷的人，读完复述演进链；复述不出就是没写清楚。

## 2. 骨架（七个锚点，顺序固定）

```text
# Vxx 标题：一句人话副标题

> 30 秒速览：3–5 行，讲清"这东西长什么样、关键结论是什么"
> 读前须知：需要先读哪卷；本卷与 v1 卷的差异（若同名）

## Where it sits     定位与边界：现象 → 职责；不覆盖什么（指向他卷）
## Evolution         演进主线：一张状态图 + 阶段表（阶段 / 触发者 / 推进单位 / 产物 / 中断）
## Stage detail      逐阶段下潜：问句标题 → 叙述 → 关键代码 → 要点卡 / 陷阱 / 改这里
## Branches          分支与层积：近战/爆炸/DLC/遗留路径/被替换的旧机制痕迹
## Contracts         契约：吃什么、吐给谁、不变量、时序约束
## Evidence          证据附录：claim 块（保号、只追加）+ 可观测点
## Open questions    真未结项，每条带 status 与取证方法
```

`## Evidence` 与 `## Open questions` 固定在最后：读者读正文时不被证据打断，需要核实时才下翻。

## 3. 叙事规则

1. **每节标题是一个问句**，例如「暖机期间到底在等什么？」「为什么命中在发射时就定了？」——问题驱动阅读，读者知道这节要解决什么。
2. **因果优先于罗列**。写"因为 A 在 B 之前，所以……"，不要只写"A 做了什么、B 做了什么"。
3. **术语首次出现给中文释义 + 英文原名**，之后只用英文原名。全卷术语需与 `docs/GLOSSARY.md` 一致。
4. **代码块只留与结论相关的语句**：不搬运无关代码；长度不限（见 3A 第 9 条）；正文用 `（见 V08-C31）` 回指证据。
5. **每个阶段必须给"推进单位"**：每 tick？每 250 tick？每帧？事件驱动？——这是 v1 最容易丢、读者最需要的信息。
6. **要点卡**：每节末尾 2–3 行 `> **要点**`，是这节的最小记忆单元。
7. **两类标注框**（至少在每卷出现一次）：
   - `> **陷阱**：……` —— 最容易读反的地方；
   - `> **改这里**：……` —— 想改数值/做 mod 应该动哪个方法。
8. **禁止**："可能/大概/应该是"这类没证据的猜测。没证据就写进 `## Open questions`。
9. **每个部分结尾给一段「这一段怎么走」**：在要点卡之后用一段散文（`**这一段怎么走**：…`，2–5 句）复述该部分的推进顺序——先做什么、再做什么、在哪个条件分叉、最后交到哪里。只讲顺序与因果，不重复数值；`##` 与 `###` 的每一节都要有。

## 3A 代码与变量的写法（强制）

1. 每个逻辑块给**两段**：`源码`（从语料原样复制、不改语句、不合并非同类行；允许用 `…` 标出省略，保留下来的行必须逐字一致）与 `伪代码`（中文、可读、与源码按语句同序对应）。
2. **每段源码前先说明功能**：固定写一段 `**这一段做什么**：…`（1–2 句，说清这段逻辑干什么、为什么截这几行、在整条链里处于哪一步），然后才是 `**源码**（方法名，截取范围；中文注释为本文档所加）`。伪代码块前标「伪代码」。
3. 伪代码用中文关键字（若 / 否则 / 返回 / 循环 / 赋值），变量名保留英文原名，缩进与源码保持同层级。
4. **新出现的变量必须解释**：卷首给「变量与类型速查」表（名称｜类型｜含义｜出处）；只在某节出现的局部变量，在该节用列表补一句。
5. 反编译出的合成名（`num`、`num2`、`flag`）**不在源码块里改名**，只在伪代码里标注业务含义（如 `num2 = 有效护甲`）。
6. **每个模块先列类结构**，用 C# 注释风格，围栏标 `csharp`（lint 会把含 `class` 的块当作类结构，跳过语句数校验）。格式：

   ```csharp
   class 类名 : 父类 {              // 这个类在本模块里扮演什么
       public Type caster;          // 该字段管什么（照抄源码的修饰符与类型）
       ...
       public virtual bool TryStartCastOn(LocalTargetInfo castTarg, LocalTargetInfo destTarg, ...)  // 函数作用（照抄源码签名）
       ...
   }
   ```

   一个模块可以有多个 `class` 块。只列与本模块相关的字段与函数，**不列函数体**；列不全时用单独一行 `...` 标出省略位置（字段区末尾、函数区末尾各一处即可），**不需要完整清单**。
   **成员一律照抄源码**：修饰符（`public` / `protected` / `private` / `virtual` / `override`）、类型、成员名、参数名与默认值都保持原样，不改名、不换中文占位符；可以删成员，但不能改写签名。
   **行尾分号按源码形态补全**：字段与抽象方法保留 `;`；属性与带方法体的方法**不加** `;`（源码本来就没有），不要为了整齐统一补分号；枚举成员用 `,` 分隔，最后一项按源码决定是否带逗号。
7. **不用编号对齐**：源码与伪代码靠「语句同序 + 同层级缩进」对应；花括号行只出现在源码里。`lint-docs.ps1 -Profile v3` 会比对相邻 `csharp`/`text` 两段的**语句数**（源码不计花括号、不计 `//` 后内容；伪代码不计纯注释行；类结构块不参与比对），不一致即报错。
8. **源码可加注释**：允许在源码行尾加中文注释（注明「注释为本文档所加」），但**不得改动语句本身**。
9. **不设行数/语句数上限**：一段逻辑该多长就多长；只有超过约 40 条语句时才考虑拆成两个模块，避免单块无法通读。

## 3B 案例（复杂逻辑必配）

- 「多步概率 / 多层削伤 / 多段时序」的逻辑，必须给一个**推演案例**：给定假设输入，逐步算出中间量与最终结果。
- 格式：假设 → 逐步计算（每步一行，保留中间值）→ 结论 →「哪些是假设、哪些是常量」。
- 数字来自 Def 数据面的标 `[假设]`；来自代码常量的标 `[常量]`。
- 案例不引入新断言；若推演结果与正文冲突，以推演为准改写正文，并补 claim。

## 4. 图表规范

- 至少一张**演进总图**（`flowchart` 或 `stateDiagram-v2`），放在 `## Evolution` 开头。
- 阶段细节可按需加 `sequenceDiagram`（跨对象时序）或决策图（`flowchart` 分支）。
- 图前一句话说明"这张图看什么"，图后 2–3 行要点；**不放大段无说明的图**。
- 节点文字用中文，标识符保留英文原名；单图节点数 ≤ 20，超了就拆。

## 5. 证据规则（不可让步）

1. claim 块格式不变：`[claim:ID]` + `src:` + `file:` + `match:`（可加 `anchor:` / `note:`）。
2. **ID 永不变号、永不复用**。v3 沿用 v1 同名卷的既有 ID；新断言从该卷最大号继续往后编。
3. `match` 必须**从语料复制**，不能手打；长度以"能唯一定位"为准，不跨行。
4. 正文引用格式：`（见 V08-C31）`；只在关键结论处引用，不逐句挂。
5. `## Evidence` 内部按阶段分组，每组一句话说明"这一组证据支撑哪一段叙述"。
6. 结论若来自"全量检索无命中"（例如某常量无人引用），必须在 claim 的 `note:` 写清检索口径。

## 6. 长度与节奏

| 项 | 建议 |
|---|---|
| 单卷 | 不限（样张 1500+ 行）；以「读得下去」为准，不为压行数删证据 |
| 单节 | 不限；超过约 300 行说明该拆模块 |
| 每节 | ≤1 图、≤3 代码块（类结构 + 源码 + 伪代码） |
| 阶段数 | 5–9 个；超过 9 个先合并 |

## 7. 目录布局

```text
docs/
  STYLE.md                       本规范
  GLOSSARY.md                    术语表（跨卷一致）
  TRACES.md                      三条端到端追踪（跨卷接力）
  CONSTANTS.md                   常量总表（脚本汇总）
  mechanisms/                    v1 卷，冻结
  mechanisms-v3/                 v3 卷，逐卷铺开
    V08-combat-and-damage.md     样张卷
```

## 8. 与 v1 的关系

- v1 卷**不改、不删、不搬**；v3 写完后 v1 作为"证据快照"保留。
- v3 正文若与 v1 冲突，以 v3 为准并在 `## Stage detail` 里注明"v1 表述为 X，实际为 Y（见 Vxx-Cyy）"。
- `scripts/verify-claims.ps1 -DocsRoot docs/mechanisms-v3` 可独立核对 v3 的断言；`scripts/lint-docs.ps1 -Profile v3` 检查 v3 结构。
