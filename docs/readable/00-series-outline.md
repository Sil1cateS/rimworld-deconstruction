# 《RimWorld 源码解析》系列大纲（讨论稿）

## 写作方向

系列按系统与模块组织，重点解析源码中的职责划分、数据结构、执行过程和模块之间的协作，再将这些实现映射到玩家熟悉的行为与画面。

问题驱动用于深入模块：谁调用它、它从哪里取得数据、怎样处理、结果交给谁、什么时候生效。游戏场景用来说明和贯通代码。

研究范围先以工作区现有的 RimWorld 1.7 语料为准。旧项目文档用于导航，具体实现回到代码核对。文中的“模块”是分析与写作的划分；对应关系要结合实际的程序集、命名空间、类型和调用确定。

## 读者与协作方式

- 作者熟悉游戏，有超过 1000 小时的游玩经验，能够阅读 C#；讨论可以直接进入类型、方法、字段和控制流。
- 成文保留必要的专业术语、代码与架构图，同时解释概念，让缺少编程背景的读者也能跟上。
- 描述代码动作时优先写明谁保存函数、谁调用、谁把数据加入队列、谁取出并处理。类型、变量、函数、继承、调用、出入队列和时空开销等常见说法保留；其他必要术语首次出现时先解释，再结合代码使用。
- “回调”要说明函数交给了谁、由谁在什么位置调用；“投递设施”“消费”“业务调用点”等概括说法，改成对应的保存、入队、取出、执行或实际调用位置，避免让读者再猜一层含义。
- MainThreadSynchronizationContext 在正文中称为“主线程待执行函数队列”，按当前实现的具体作用说明；源码中的类名、字段名和函数名保持原样。
- 引用源码时保留原有命名。确需为阅读改名，必须在片段之前逐项说明“源码名 → 本文暂用名”，只写“简化变量名”不足以说明对应关系；示意代码另行注明。
- 文档、图片和图源链接使用相对于当前 Markdown 文件的路径，统一使用 `/` 分隔，遵循 [GitHub 的相对链接规则](https://docs.github.com/en/get-started/writing-on-github/getting-started-with-writing-and-formatting-on-github/basic-writing-and-formatting-syntax#relative-links)。
- `analysis/decompiled/` 不随仓库分发。源码引用采用“命名空间.类型名.cs:行号”的文字定位，例如 `RimWorldWaylith.Bootstrap.cs:749`。命名空间和类型名取自源码，行号对应当前反编译文件，供本地核对。
- 展开类的方法之前，先按需要说明该类持有的主要数据、涉及的对象是什么，以及继承关系怎样影响它们的处理方式。
- 先讨论模块边界与主要问题，再查代码、组织解释、逐段成稿。
- 一个模块可以衍生多篇文章。先确定覆盖范围与依赖关系，再决定篇数和标题。
- 资料、讨论记录和成稿统一放在 `docs/readable/`，采用本工作线单独讨论的写作方式。

## 一个模块需要解释什么

下面是调查和讨论的要点，成文时可以根据模块特点安排结构：

1. **职责与边界**：它解决什么问题，哪些工作属于相邻系统？
2. **入口与时机**：谁调用它，通过每帧、每 tick、事件、查询还是显式命令进入？
3. **核心数据与类型**：状态由谁持有，哪些是定义、实例、索引、缓存或运行中的对象？
4. **内部执行过程**：一次调用怎样推进，重要分支、失败、中断和恢复发生在哪里？
5. **模块之间的协作**：向谁查询，调用谁，返回或修改什么；哪些步骤跨线程、跨帧或跨 tick？
6. **游戏中的对应结果**：将关键状态与行为、画面、声音和界面对应起来。

图中应区分调用、返回的数据、状态变化和异步交接。概念关系图与具体调用链分别说明范围，避免用一条箭头代替未经核对的中间过程。

## 两个模块的展开示例

### Waylith：按一条线性主线组织

1. **Waylith 总览**：先用总图认识启动、主线程、渲染线程与 Vulkan 的关系。
2. **引擎创建**：从 Program.Main 进入 EngineApplication，说明窗口、设备、FrameRenderer 等对象怎样建立。
3. **初始化**：按 Bootstrap.Initialize 的工作顺序，说明兼容运行时、更新函数、输入、绘制与初始场景怎样接入。
4. **两条线程与三个队列**：先介绍主线程、渲染线程，以及主线程待执行函数队列、渲染回调队列、帧数据队列；具体规则在后面的调用位置展开。
5. **主线程**：总览 → 按工作顺序阅读 RunLoop → 主线程队列泵 → OnUpdate → 采集渲染 → 限速。
6. **渲染线程**：从队列取包，准备绘制资源，调用各模块记录 Vulkan 指令。
7. **渲染数据的交换与提交**：把两端连起来，解释入队、取包、满与空时的等待，再走到图形提交和呈现。

文章沿启动、调用与数据交接的顺序展开。实际运行时，主线程、渲染线程与 GPU 可以同时推进各自的工作。

需要分别定义 frame 所指的引擎循环、时间信息、RenderFrame 数据包和最终显示图像，沿实际代码说明它们的关系。

已核对的调用关系：`EngineApplication.RunLoop` 调用 `OnUpdate`；`Bootstrap.Initialize` 保存的更新函数推进兼容运行时；随后主循环调用 `FrameRenderer.CaptureFrame`，得到 `RenderFrame` 并交给 `RenderThread.Enqueue`。Waylith 篇说明接口调用、线程顺序和 Vulkan 提交位置。特性返回什么结构、地图与 UI 怎样形成这些数据、各 pass 怎样绘制，留给后续渲染模块；已有材料收在 [渲染模块资料](15-rendering-module-notes.md)。

### 工作系统：建议区分选择与执行

1. **调用的起点**：Pawn 的任务跟踪器何时请求下一项任务，决策树怎样进入工作选择。
2. **候选来源**：工作设置怎样排列 WorkGiver；各类工作怎样查询地图对象、格子、标记或账单等条件。
3. **筛选和形成 Job**：能力、限制、优先级、可达性等怎样影响选择；预留怎样参与筛选与启动。
4. **交回任务运行系统**：Job 怎样返回给 Pawn 的任务跟踪器，再由 JobDriver 与 Toil 推进，处理失败、中断和结束。
5. **进入具体动作**：移动、搬运、生产各自调用哪些功能；需要使用 Verb 的任务怎样选定并调用它。

已核对的接缝：`JobGiver_Work.TryIssueJobPackage(Pawn, ...)` 按该 Pawn 的工作设置选择 WorkGiver，扫描分支取得候选目标后通过 `JobOnThing` 或 `JobOnCell` 生成 Job，并以 ThinkResult 返回。`Pawn_JobTracker` 通过决策得到结果后调用 `StartJob`。`Toils_Combat.CastVerb` 是任务执行阶段调用 `Verb.TryStartCastOn` 的一个明确例子。

这些接缝用于确定讨论方向。各类工作的特殊候选来源、其他任务入口和动作路径，研究具体模块时补全。

## 写作顺序建议与待讨论事项

- 先建立一张总架构图，说明引擎、兼容层、游戏调度、地图、实体、行为和表现之间的主要连接。
- 第一组可从 Waylith 及其与游戏、渲染的接缝展开，确定系列需要的源码深度、术语解释与图示方式。
- 完成地图、空间和 UI 的解析后，再详细研究渲染模块；Waylith 篇的绘制部分保留采集、线程交接、指令记录、提交与呈现的主线。
- 工作模块适合随后作为跨系统样例，检验地图查询、Pawn 决策、任务执行和动作调用能否讲得连贯。
- 模块目录先保持完整。研究到每个模块时，再讨论如何拆篇、用哪些场景说明，以及哪些细节值得进入正文。
- 人物绘制、光照、音频及 DLC 独有机制需要补查。渲染提交的主线已读通，具体 pass、数据结构与资源服务留在后续渲染模块展开；涉及实际耗时、帧率和瓶颈的结论，需要相应观察或测量。
